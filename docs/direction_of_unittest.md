# 単体テスト作成方針

## 基本方針

単体テストは、実装の詳細ではなく、対象の振る舞いと期待する結果を読み手がすぐ理解できることを重視する。各テストは独立して実行でき、失敗したときに「どの条件で、何が期待と異なったか」が分かるようにする。

## ファイルの配置と命名

- テスト対象の `src` 以下のディレクトリ構成を `__tests__/unit` 以下に再現する。
- テストファイル名は原則として対象モジュール名に `.test.ts` を付ける。例: `src/common/coordinate.ts` に対して `__tests__/unit/common/coordinate.test.ts`。
- 1つのモジュールを観点ごとに分割する場合は、同じ場所に `<モジュール名>.<観点>.test.ts` として置く。分割後も対象モジュールとの対応が分かる名前にする。
- 複数のテストで共有するテスト用ヘルパーは `__tests__/unit/util` に置く。テスト対象のコードと混同しない名前にする。

## テストの構成

- テストランナーは `node:test` の `describe` と `it` を使う。`test` など別のテスト宣言 API と混在させない。
- `describe` は対象のクラス、関数、または振る舞いをまとめる。必要な場合に限り、メソッド名や状態・条件ごとに入れ子にする。
- `it` は1つの振る舞い・期待結果を検証する。異なる理由で失敗するケースは別の `it` に分ける。
- 各テストは原則として **初期化（Arrange）→ 操作（Act）→ 検証（Assert）** の順に書く。
  1. **初期化**: 入力、対象オブジェクト、モックや前提状態を準備する。
  2. **操作**: 検証したい関数・メソッドを呼び出す、またはイベントを発生させる。
  3. **検証**: 戻り値、状態、イベント、呼び出し回数など、期待する結果を確認する。
- 操作がない初期値・プロパティのテストでは、初期化のあとに対象の値を検証する。例外のテストでは、操作を `assert.throws` などで囲んで検証する。
- `beforeEach` / `afterEach` などのフックは、DOM の準備・復元など複数テストで共通する前提に使う。個別テストの重要な前提や操作は、テスト本文に残して読み手が追えるようにする。

## 説明文の書き方

- 説明文は日本語で統一する。テスト対象のクラス名やメソッド名など、コード上の識別子は必要に応じてそのまま使ってよい。
- `describe` は「何をテストするか」を短く示す。例: `describe('MineField の振る舞い')`、`describe('コンストラクター')`、`describe('イベントとスコア')`。
- `it` はテストの条件と期待される振る舞いを具体的に示す。「～のとき、～する」「～すると、～になる」のような簡潔な文を基本とする。例: `it('セルをクリックすると、周囲の空マスを開く')`。
- `should` の有無や `[click]` のような記号付き表記、`unittest:` の接頭辞は使わない。
- 「テストケース1」「正常に動く」のような、期待結果や条件が説明文だけでは分からない表現は避ける。
- 説明文は実装手順ではなく、利用者から見た結果を表す。例えば「メソッドを呼ぶ」だけでなく、「呼び出すと状態が変化する」のように書く。

## 検証とテストデータ

- `node:assert/strict` の適切なアサーションを使い、期待値と実際の結果が明確に比較できるようにする。配列・オブジェクトの全体比較には `deepEqual`、同一性の比較には `strictEqual` などを使い分ける。
- 戻り値だけでなく、対象の状態変化やイベントなど、その振る舞いに必要な副作用も検証する。一方で、無関係な内部実装の詳細に依存しない。
- 1つのテスト内の複数の検証は、同じ振る舞いを説明する範囲にまとめる。無関係な期待を一つのテストに詰め込まない。
- 同じ振る舞いを複数の入力で確認するときは、必要に応じてテストケースを配列などにまとめる。各ケースの条件が読み取れる説明を付け、単なる連番だけにしない。
- モックやグローバル状態は必要最小限にし、テストごとに初期化・復元して他のテストに影響させない。乱数など非決定的な処理は、可能な限り結果そのものではなく保証すべき性質を検証する。

## コメントの方針

- テスト名とコードだけでは、テストの前提・操作の理由・期待結果の意図が読み取れない場合は、補足コメントを追加する。
- コメントには「なぜこの前提や操作が必要か」「何を確認するためのケースか」など、コードやテスト名だけでは不足する情報を書く。
- コメントは不足している説明を補うために使い、テスト名や直後のコードを言い換えるだけのコメント（例: `// クリックする` の直後にクリック処理を書く）は追加しない。
- コメントは該当する準備や検証の近くに置き、短く具体的に記述する。

## 基本形

```ts
void describe('対象の名前', () => {
    void it('期待される振る舞いを条件とともに説明する', () => {
        const target = createTarget();

        target.performAction();

        assert.equal(target.state, 'expected');
    });
});
```
